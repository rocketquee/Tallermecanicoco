1. Objetivo del sistema

1.1 Contexto del negocio

Pizarro Performance Garage atiende autos de lujo y trabaja con clientes VIP y figuras públicas. La operación diaria se lleva en libretas y hojas de Excel: las órdenes se anotan a mano, el inventario se revisa de memoria y los pagos se concilian al final del día. Ese esquema produce tres problemas concretos:

  1. Pérdida de trazabilidad. No se puede reconstruir quién autorizó una compra, quién movió una pieza o cuándo cambió una orden de etapa.
  2. Riesgo de discreción. El nombre de un cliente público queda visible para cualquier persona que abra la libreta o el archivo compartido.
  3. Decisiones sin datos. El dueño no sabe cuánto vale el inventario detenido, cuántos autos están en el taller ni cuánto se ha cobrado.

AutoPulse Elite sustituye ese esquema por una aplicación web con permisos por rol, bitácora inmutable y una base de datos que impone las reglas de negocio.

1.2 Objetivo general

Diseñar e implementar un sistema web de gestión para Pizarro Performance Garage que concentre clientes, vehículos, órdenes de servicio, inventario y usuarios, con trazabilidad completa, control de acceso por rol y protección de la información confidencial.

1.3 Objetivos específicos

  • Modelar en MySQL 8.x un esquema relacional normalizado que soporte la operación completa del taller y que impida borrados accidentales.
  • Implementar una API REST con FastAPI, autenticación JWT y autorización por rol y por fila.
  • Construir una interfaz React + TypeScript usable en computadora, tableta y celular.
  • Garantizar que toda operación sensible quede registrada en una bitácora inmutable.
  • Documentar el modelo con un diagrama E-R interactivo y un diccionario de datos navegable.

1.4 Alcance

Incluido en esta fase: autenticación, clientes, vehículos, órdenes de servicio con cuatro etapas, inventario, usuarios, panel principal y auditoría.

Fuera de esta fase: proveedores y compras internacionales, pagos y saldos, facturación CFDI 4.0 con timbrado, reportes exportables, fotos del vehículo y pólizas de seguro. Las tablas de esos módulos ya existen en el modelo; lo que falta son los endpoints y las pantallas.

2.7 Criterio de aceptación del primer día

Abrir orden ORD-01 Sí POST /ordenes; nace en Recibido.

3. Software, lenguajes y herramientas

3.1 Criterio de selección

El taller tiene cinco usuarios, unos ocho ingresos por semana y diez autos simultáneos (SEG-14). Ese tamaño descarta un clúster, colas de mensajes o microservicios. La restricción real es otra: el sistema debe ser mantenible por una sola persona y auditable, porque cada peso cobrado y cada pieza que sale del almacén debe poder justificarse meses después.

Por eso se eligió una arquitectura de tres capas con tecnologías maduras, gratuitas y con documentación abundante.

3.2 Tecnologías y justificación

4.2 Ingeniería inversa: del DDL a los modelos

En este proyecto la ingeniería inversa no consistió en adivinar un esquema desconocido. El DDL de sql/ fue la fuente de verdad y los modelos SQLAlchemy se derivaron de él, verificando después que coincidieran con la base real. El orden fue:

  1. Diseño del DDL por bloques, con comentarios por columna y requisito asociado.
  2. Creación de los modelos en backend/app/models/, una clase por tabla, con Mapped[...], mapped_column(...) y relationship(...).
  3. Verificación con el inspector de SQLAlchemy: se compararon nombres de tablas, columnas, tipos, nulabilidad, llaves y valores de ENUM.
  4. Ajuste de discrepancias en el DDL o en el modelo, siempre con el DDL como árbitro.

4.2.2 Del DDL de MySQL al modelo SQLAlchemy

La ingeniería inversa se concretó en un archivo por tabla dentro de backend/app/models/. Cada clase hereda de Base (declarativa de SQLAlchemy 2.x) y declara __tablename__, columnas con Mapped[...] y mapped_column(...), y relaciones con relationship(...). La regla fue una columna del DDL, una columna del modelo, sin inventar campos ni ocultar restricciones.

Ejemplo 1: tabla clientes. El DDL físico define el id, el nombre, la categoría ENUM, el descuento y el borrado lógico:

CREATE TABLE clientes (
  id INT UNSIGNED NOT NULL AUTO_INCREMENT,
  nombre VARCHAR(150) NOT NULL,
  categoria ENUM('Regular','VIP') NOT NULL DEFAULT 'Regular',
  descuento_mano_obra DECIMAL(5,2) NOT NULL DEFAULT 0.00,
  activo TINYINT(1) NOT NULL DEFAULT 1,
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

El modelo equivalente en backend/app/models/clientes.py conserva tipo, nulabilidad, valor por defecto e índice:

class Cliente(Base):
    __tablename__ = "clientes"
    __table_args__ = (
        Index("idx_clientes_nombre", "nombre"),
        Index("idx_clientes_categoria", "categoria"),
        {"mysql_engine": "InnoDB", "mysql_charset": "utf8mb4",
         "mysql_collate": "utf8mb4_unicode_ci"},

    id: Mapped[int] = mapped_column(
        INTEGER(unsigned=True), primary_key=True, autoincrement=True
    )
    nombre: Mapped[str] = mapped_column(String(150), nullable=False)

        Enum("Regular", "VIP", name="categoria_cliente"),
        nullable=False,
        server_default="Regular",
    )
    descuento_mano_obra: Mapped[Decimal] = mapped_column(
        Numeric(5, 2), nullable=False, server_default=text("0.00")
    )
    activo: Mapped[bool] = mapped_column(

    vehiculos: Mapped[list["Vehiculo"]] = relationship(back_populates="cliente")

Decisiones de traducción que evitaban errores silenciosos:

  1. Nulabilidad explícita. Mapped[str] describe una columna NOT NULL; Mapped[str | None] describe una columna que acepta NULL. Además se escribe nullable=False en las columnas obligatorias para que el DDL generado coincida sin ambigüedad.
  2. Valores por defecto del servidor. Se usó server_default=text("0") o server_default="Regular" para que el valor lo ponga MySQL, igual que en el DDL, y no solo Python al insertar.
  3. updated_at con onupdate=func.now(). Refleja el ON UPDATE CURRENT_TIMESTAMP del DDL.
  4. Comentarios y motor. __table_args__ conserva mysql_engine, mysql_charset, mysql_collate y el comentario de la tabla, de modo que SHOW CREATE TABLE y el modelo cuenten la misma historia.
  5. Relaciones sin duplicar columnas. relationship() no crea columnas nuevas: solo navega la FK que ya existe en el DDL. Por eso Cliente.vehiculos no añade cliente_id a vehiculos.

La comprobación final se hizo con sqlalchemy.inspect(engine) (sección 4.2.1): 21 tablas, 218 columnas, 24 llaves foráneas y 59 índices coincidentes. Cuando el inspector y el modelo discrepaban, se corrigió el modelo; el DDL siempre fue el árbitro.

4.3 Llaves primarias y llaves foráneas

Llave primaria. Todas las tablas usan id INT UNSIGNED NOT NULL AUTO_INCREMENT como PK. Es un identificador sustituto, estable y compacto, que no cambia aunque el negocio cambie (un RFC o una placa pueden corregirse; el id no). Las tablas de detalle conservan además su unicidad real:

  • detalle_orden: una línea es un servicio o una refacción, nunca ambos.
  • detalle_compra: una compra no repite la misma refacción.
  • orden_mecanicos: UNIQUE (orden_id, mecanico_id) impide asignar dos veces al mismo técnico.

Llave foránea. Las 24 relaciones se declaran con FOREIGN KEY, nombre fk_<tabla>_<referencia>, ON DELETE RESTRICT y ON UPDATE CASCADE:

CONSTRAINT fk_vehiculos_cliente
  FOREIGN KEY (cliente_id) REFERENCES clientes (id)
  ON DELETE RESTRICT ON UPDATE CASCADE

Ejemplos representativos:

Tabla hija Columna Tabla padre Regla de negocio
vehiculos cliente_id clientes Un auto siempre tiene dueño.
ordenes_servicio cliente_id clientes La orden conserva al cliente aunque se abra desde el vehículo.
ordenes_servicio vehiculo_id vehiculos No se puede abrir una orden para un auto inexistente.
ordenes_servicio mecanico_id mecanicos Responsable principal; los participantes viven en orden_mecanicos.
detalle_orden orden_id ordenes_servicio El detalle no existe sin orden.
pagos, facturas, autorizaciones orden_id ordenes_servicio Todo movimiento financiero cuelga de una orden.

Por qué ON DELETE RESTRICT. Si se borrara un cliente, sus órdenes quedarían sin dueño y la facturación histórica perdería sentido. Con RESTRICT, la base impide el borrado incluso si alguien ejecuta SQL a mano. La baja se hace apagando activo (borrado lógico, SEG-07).

4.4 Normalización

El esquema está en tercera forma normal (3FN), con tres desnormalizaciones deliberadas.

Primera forma normal (1FN)

Todos los atributos son atómicos: no hay listas separadas por comas ni campos multivalor. La única excepción aparente son clientes.telefono1 y clientes.telefono2, que no violan 1FN porque CLI-01 fija exactamente dos teléfonos. Una tabla telefonos habría permitido un número arbitrario, pero también habría obligado a un JOIN en cada consulta para un dato que siempre son dos columnas. Se documenta como decisión consciente.

Segunda forma normal (2FN)

No hay dependencias parciales: todos los atributos dependen de la llave completa. Las tablas de detalle usan id sustituto como PK, pero su unicidad real es la combinación de la cabecera con el concepto, y ningún atributo depende solo de una parte.

Tabla Llave real Atributos que dependen de ella
detalle_orden (orden_id, servicio_id) o (orden_id, refaccion_id) cantidad, precio_unitario, activo
detalle_compra (compra_id, refaccion_id) cantidad, precio_unitario_moneda, activo
orden_mecanicos (orden_id, mecanico_id) created_at, activo

Tercera forma normal (3FN)

No hay dependencias transitivas: el nombre del cliente no se repite en la orden, el nombre del proveedor no se repite en la refacción y el precio del servicio no se copia en cada línea. Se accede por JOIN.

Dato Dónde vive Dónde no se duplica
Nombre y contacto del cliente clientes ordenes_servicio solo guarda cliente_id.
Marca y modelo del auto vehiculos ordenes_servicio solo guarda vehiculo_id.
Nombre del proveedor proveedores refacciones solo guarda proveedor_id.
Nombre y precio del servicio servicios detalle_orden guarda una copia histórica del precio, no del nombre.

Casos concretos de 3FN en el esquema

La tercera forma normal exige que ningún atributo que no sea llave dependa de otro atributo que tampoco sea llave. Dicho de forma simple: si A → B y B → C, entonces C no debe vivir en la misma tabla que A. Estos son los casos que se corrigieron al diseñar AutoPulse Elite.

Caso 1: por qué proveedores se separó de refacciones.

Si refacciones guardara el nombre, el país, el contacto y el teléfono del proveedor, existiría esta dependencia transitiva:

refaccion.id → refaccion.proveedor_id → proveedor.nombre, proveedor.contacto, proveedor.telefono

El nombre del proveedor no depende de la refacción, sino del proveedor. Con la tabla separada, un cambio de teléfono se hace una sola vez en proveedores y todas las refacciones lo ven por JOIN. Además se evita el error clásico de que la misma refacción tenga dos teléfonos distintos según la fila que se consulte.

Si estuviera desnormalizado Cómo está en el esquema Qué se gana
refacciones(id, nombre, proveedor_nombre, proveedor_pais, proveedor_contacto, ...) proveedores(id, nombre, pais, contacto, telefono, correo, ...) + refacciones.proveedor_id Un proveedor se edita una vez; no hay datos contradictorios.
El país se repite en cada pieza importada. El país vive en proveedores.pais. Reportes por país sin DISTINCT ni cadenas duplicadas.
Borrar un proveedor dejaría texto huérfano. FOREIGN KEY ... ON DELETE RESTRICT. La base impide dejar refacciones sin proveedor.

Caso 2: por qué clientes no se repite en ordenes_servicio.

ordenes_servicio guarda cliente_id, no el nombre ni el teléfono. Si los copiara, el nombre dependería del cliente y no de la orden:

orden.id → orden.cliente_id → cliente.nombre, cliente.telefono, cliente.confidencial

Esa copia sería especialmente peligrosa con clientes confidenciales: una orden vieja podría conservar el nombre real aunque el cliente ya se haya marcado como confidencial. Al normalizar, el enmascaramiento se decide en un solo lugar (clientes.confidencial) y aplica a todo el historial.

Caso 3: por qué servicios no se copia en detalle_orden.

El detalle guarda servicio_id, cantidad y precio_unitario. El nombre y la duración del servicio viven en servicios. La única copia deliberada es el precio, porque una orden debe conservar lo que se cobró aunque el catálogo suba de precio; esa excepción se documenta en la sección de desnormalizaciones.

Caso 4: por qué vehiculos y mecanicos tienen su propia tabla.

La placa, la marca y el modelo dependen del vehículo, no de la orden. El nombre y la especialidad dependen del mecánico, no de la asignación. Por eso ordenes_servicio solo guarda vehiculo_id y mecanico_id, y los participantes adicionales viven en la tabla puente orden_mecanicos (orden_id, mecanico_id, created_at). Así un mecánico puede participar en muchas órdenes sin duplicar su ficha.

Cómo se verificó la 3FN. Para cada tabla se comprobó que:

  1. Todos los atributos son atómicos (1FN).
  2. Todos los atributos no llave dependen de la llave completa, no de una parte (2FN).
  3. Ningún atributo no llave depende de otro atributo no llave (3FN).

El resultado son 21 tablas donde los datos de contacto, catálogo y precios viven en su tabla de origen y las tablas transaccionales solo guardan llaves y los valores históricos que la auditoría exige conservar.

4.7.1 Anatomía y código de los triggers

Un trigger es un bloque SQL que el motor ejecuta automáticamente ante un evento de una tabla. Sus partes son:

Parte Significado
BEFORE / AFTER Si se ejecuta antes o después de la operación. En BEFORE se puede validar y cancelar con SIGNAL; en AFTER ya no se puede impedir el cambio.
INSERT / UPDATE / DELETE Evento que lo dispara.
FOR EACH ROW Se ejecuta una vez por cada fila afectada (obligatorio en MySQL).
NEW Fila con los valores nuevos (INSERT y UPDATE).
OLD Fila con los valores anteriores (UPDATE y DELETE).
SIGNAL SQLSTATE '45000' Aborta la operación con un mensaje propio; MySQL lo reporta como error de usuario.

Trigger de exclusividad (XOR) del detalle de orden:

DELIMITER $$
CREATE TRIGGER trg_detalle_orden_bi BEFORE INSERT ON detalle_orden
FOR EACH ROW
BEGIN
  IF (NEW.servicio_id IS NULL AND NEW.refaccion_id IS NULL)
     OR (NEW.servicio_id IS NOT NULL AND NEW.refaccion_id IS NOT NULL) THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT = 'detalle_orden: debe indicar servicio_id o refaccion_id, pero no ambos';
  END IF;
END$$
DELIMITER ;

Trigger de inmutabilidad de la bitácora:

DELIMITER $$
CREATE TRIGGER trg_bitacora_bu BEFORE UPDATE ON bitacora
FOR EACH ROW
BEGIN
  SIGNAL SQLSTATE '45000'
    SET MESSAGE_TEXT = 'bitacora: es inmutable, no se permite modificar asientos';
END$$
DELIMITER ;

El trigger trg_bitacora_bd es idéntico, pero con BEFORE DELETE. historial_etapas repite el mismo par. Así, ni un UPDATE accidental desde Workbench ni un DELETE desde la API pueden alterar el rastro de auditoría.

4.8 Procedimientos almacenados, funciones y transacciones

4.8.1 Qué son y por qué se agregaron

Un procedimiento almacenado (stored procedure) es un bloque SQL con nombre que se guarda en el servidor y se ejecuta cuando alguien lo invoca con CALL. Se diferencia de un trigger en que no se dispara solo: lo llama la aplicación, un script o un usuario con permisos. Admite parámetros de entrada (IN), de salida (OUT) y de entrada-salida (INOUT), variables locales, control de flujo (IF, CASE, LOOP) y manejo de errores.

Una función almacenada (stored function) también vive en el servidor, pero se usa como una expresión: recibe parámetros, devuelve un solo valor con RETURN y puede aparecer dentro de un SELECT, un WHERE o una asignación. Un procedimiento ejecuta acciones y puede devolver uno o varios result sets; una función siempre devuelve un valor.

La diferencia con un trigger es clara: el trigger se dispara automáticamente ante un INSERT, UPDATE o DELETE; el procedimiento y la función se invocan a propósito.

En la versión 1.1 de este reporte se había decidido no desplegar rutinas. Para el cierre de los criterios de evaluación se agregó sql/11_procedimientos_funciones.sql, ejecutado contra la base real autopulse_elite en MySQL 26.7.0. La API sigue siendo la dueña de las transacciones; las rutinas cubren dos operaciones concretas y se verificaron con CALL y SELECT.

4.8.2 Procedimiento sp_calcular_total_orden

Firma: sp_calcular_total_orden(IN p_orden_id INT UNSIGNED).

Qué hace: lee el detalle vigente de la orden, separa piezas y mano de obra, aplica el descuento VIP del cliente, calcula el IVA del 16 %, guarda los cinco importes en ordenes_servicio y devuelve un renglón con el desglose.

Reglas aplicadas:

  1. total_piezas = suma de líneas con refaccion_id.
  2. mano_obra_bruta = suma de líneas con servicio_id.
  3. descuento_vip_pct = clientes.descuento_mano_obra, acotado entre 0 y 100.
  4. total_mano_obra = mano_obra_bruta × (100 − descuento) / 100.
  5. subtotal = total_piezas + total_mano_obra.
  6. iva = subtotal × 0.16.
  7. total = subtotal + iva.
DELIMITER $$
CREATE PROCEDURE sp_calcular_total_orden(IN p_orden_id INT UNSIGNED)
    MODIFIES SQL DATA
BEGIN
    DECLARE v_existe INT DEFAULT 0;
    DECLARE v_descuento DECIMAL(5,2) DEFAULT 0.00;
    DECLARE v_piezas DECIMAL(12,2) DEFAULT 0.00;
    DECLARE v_mano_obra_bruta DECIMAL(12,2) DEFAULT 0.00;
    DECLARE v_mano_obra DECIMAL(12,2) DEFAULT 0.00;
    DECLARE v_subtotal DECIMAL(12,2) DEFAULT 0.00;
    DECLARE v_iva DECIMAL(12,2) DEFAULT 0.00;
    DECLARE v_total DECIMAL(12,2) DEFAULT 0.00;

    SELECT COUNT(*) INTO v_existe
      FROM ordenes_servicio
     WHERE id = p_orden_id AND activo = 1;

    IF v_existe = 0 THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'La orden indicada no existe o esta dada de baja';
    END IF;

    SELECT COALESCE(SUM(CASE WHEN d.refaccion_id IS NOT NULL
                             THEN d.precio_unitario * d.cantidad ELSE 0 END), 0.00),
           COALESCE(SUM(CASE WHEN d.servicio_id IS NOT NULL
                             THEN d.precio_unitario * d.cantidad ELSE 0 END), 0.00)
      INTO v_piezas, v_mano_obra_bruta
      FROM detalle_orden d
     WHERE d.orden_id = p_orden_id AND d.activo = 1;

    -- El descuento VIP vive en clientes, no se repite en la orden (3FN).
    SELECT c.descuento_mano_obra INTO v_descuento
      FROM ordenes_servicio o
      JOIN clientes c ON c.id = o.cliente_id
     WHERE o.id = p_orden_id;

    IF v_descuento < 0 THEN SET v_descuento = 0.00;
    ELSEIF v_descuento > 100 THEN SET v_descuento = 100.00;
    END IF;

    SET v_piezas = ROUND(v_piezas, 2);
    SET v_mano_obra = ROUND(v_mano_obra_bruta * (100 - v_descuento) / 100, 2);
    SET v_subtotal = ROUND(v_piezas + v_mano_obra, 2);
    SET v_iva = ROUND(v_subtotal * 0.16, 2);
    SET v_total = ROUND(v_subtotal + v_iva, 2);

    UPDATE ordenes_servicio
       SET total_piezas = v_piezas,
           total_mano_obra = v_mano_obra,
           subtotal = v_subtotal,
           iva = v_iva,
           total = v_total
     WHERE id = p_orden_id;

    SELECT p_orden_id AS orden_id,
           v_piezas AS total_piezas,
           v_mano_obra_bruta AS mano_obra_bruta,
           v_descuento AS descuento_vip_pct,
           v_mano_obra AS total_mano_obra,
           v_subtotal AS subtotal,
           v_iva AS iva,
           v_total AS total;
END$$
DELIMITER ;

4.8.3 Función fn_valor_en_custodia

Firma: fn_valor_en_custodia().

Qué hace: suma vehiculos.valor_aproximado de los autos que siguen bajo custodia del taller, es decir, los que tienen al menos una orden vigente cuyo estado no es Entregado. Devuelve un DECIMAL(14,2) en pesos.

DELIMITER $$
CREATE FUNCTION fn_valor_en_custodia()
    RETURNS DECIMAL(14,2)
    READS SQL DATA
BEGIN
    DECLARE v_total DECIMAL(14,2) DEFAULT 0.00;

    SELECT COALESCE(SUM(v.valor_aproximado), 0.00)
      INTO v_total
      FROM vehiculos v
     WHERE v.activo = 1
       AND v.valor_aproximado IS NOT NULL
       AND EXISTS (
           SELECT 1
             FROM ordenes_servicio o
            WHERE o.vehiculo_id = v.id
              AND o.activo = 1
              AND o.estado <> 'Entregado'
       );

    RETURN v_total;
END$$
DELIMITER ;

Por qué EXISTS y no un JOIN: un vehículo puede tener varias órdenes abiertas (por ejemplo, una reparación y una revisión posterior). Con EXISTS el vehículo se cuenta una sola vez; con un JOIN directo se sumaría una vez por cada orden. Los vehículos sin orden —un auto recién registrado— no están en custodia y no suman.

La condición se aplica literalmente: Listo sigue contando porque el auto espera la entrega, y Cancelado también cuenta mientras el vehículo no se haya retirado físicamente. Si el taller define que una orden cancelada libera el auto de inmediato, el predicado se cambia por o.estado NOT IN ('Entregado', 'Cancelado') sin tocar el resto de la función.

Ejecución real:

SELECT fn_valor_en_custodia() AS valor_en_custodia_mxn;
valor_en_custodia_mxn
5 860 000.00

El resultado se compone de los vehículos con orden abierta: 2 450 000 + 980 000 + 520 000 + 1 150 000 + 760 000. El vehículo entregado (420 000) y el vehículo sin orden (11 500 000) quedan fuera, que es exactamente lo que debe mostrar el tablero.

Integración con la aplicación. El backend expone GET /api/v1/dashboard/valor-custodia (backend/app/routers/dashboard.py), que ejecuta SELECT fn_valor_en_custodia() y responde:

{"valor": "5860000.00", "moneda": "MXN", "fuente": "fn_valor_en_custodia"}

El endpoint está restringido al rol Administrador porque es un dato económico (SEG-18). El frontend lo consume desde frontend/src/services/dashboard.ts y el indicador “Valor en custodia” de Dashboard.tsx muestra ese valor; ya no se suman vehículos en el navegador. La tarjeta indica “Calculado con fn_valor_en_custodia()” para que la evidencia sea explícita.

4.8.6 Transacciones y atomicidad

Toda operación que toca más de una tabla se ejecuta en una sola transacción. El caso más complejo es POST /api/v1/ordenes/{id}/registrar-avance, que puede escribir hasta en seis tablas: ordenes_servicio, detalle_orden, refacciones, movimientos_inventario, historial_etapas y bitacora. El orden importa:

  1. Bloquear refacciones antes de tocar la orden, con SELECT ... FOR UPDATE, ordenadas por refaccion_id. Si dos mecánicos usan las mismas piezas, el orden fijo de adquisición de locks evita el interbloqueo.
  2. Validar stock dentro del lock. Si no alcanza, se responde 400 con la cantidad disponible y no se escribe nada.
  3. Insertar el detalle y descontar existencias, dejando un movimiento de inventario por pieza.
  4. db.flush() para que los INSERT lleguen a la transacción y los totales puedan recalcularse leyendo el detalle recién insertado.
  5. Recalcular totales (piezas, mano de obra con descuento VIP, IVA y total).
  6. Escribir historial_etapas y bitacora con el usuario autenticado.
  7. db.commit() una sola vez. Ante cualquier excepción, db.rollback() deja la base como estaba.
# Se bloquean las refacciones antes de tocar la orden para que dos mecanicos
# no puedan dejar el stock en negativo. Se ordenan por id para que las
# transacciones tomen los locks siempre en el mismo orden.
refacciones: list[tuple[int, Refaccion]] = []
for item in sorted(payload.refacciones, key=lambda linea: linea.refaccion_id):
    refaccion = db.scalars(
        select(Refaccion)
        .where(Refaccion.id == item.refaccion_id)
        .with_for_update()
    ).first()
    if refaccion is None or not refaccion.activo:
        raise HTTPException(status_code=400, detail="...")
    if refaccion.stock_actual < item.cantidad:
        raise HTTPException(status_code=400, detail="Stock insuficiente ...")
    refacciones.append((item.cantidad, refaccion))

try:
    ...
    db.flush()
    _recalcular_totales(db, orden)
    ...
    db.commit()
except OperationalError as exc:
    db.rollback()
    ...

flush() y no commit() intermedio: enviar los INSERT sin confirmar permite obtener los AUTO_INCREMENT para las tablas hijas sin abrir la puerta a un estado a medias. Un commit() intermedio dejaría una orden creada sin historial si el siguiente INSERT fallara.

Situación Error MySQL Respuesta de la API

Concurrencia. InnoDB trabaja con REPEATABLE READ (predeterminado de MySQL 8). Los dos puntos donde la concurrencia podría causar daño se resolvieron con bloqueo pesimista (FOR UPDATE) para el stock y con UNIQUE (orden_id, mecanico_id) para la doble asignación.

Contenido y vigencia del token. JWT firmado con HS256 y la clave JWT_SECRET_KEY del .env. Su contenido es mínimo a propósito:

Claim Valor Uso
sub id del usuario Identificar la cuenta.
correo Correo del usuario Mostrar en la interfaz y trazabilidad.
rol Administrador, Recepcion o Mecanico Informativo; no es la autoridad final.
tipo access Distinguir el tipo de token.
iat Momento de emisión Auditoría.
exp Emisión + 480 minutos (8 h) Expiración.

No se incluyen datos personales, precios ni permisos: un JWT se puede decodificar sin la clave, así que todo lo que va dentro debe considerarse público. El rol es informativo porque el backend recarga el usuario desde la base en cada petición:

def get_current_user(token: str = Depends(oauth2_scheme), db: Session = Depends(get_db)):
    try:
        payload = decodificar_token(token)
    except TokenInvalido:
        raise _CREDENCIALES_INVALIDAS
    usuario = db.get(Usuario, int(payload["sub"]))
    if usuario is None or not usuario.activo:
        raise _CREDENCIALES_INVALIDAS
    return usuario

Ese detalle resuelve un problema real: si el administrador degrada a un mecánico o da de baja una cuenta, el cambio surte efecto de inmediato, sin esperar a que expire el token.

No hay refresh token. Al expirar, el usuario vuelve a iniciar sesión. Para una jornada de 8 horas es suficiente y elimina la superficie de ataque de un token de renovación de larga vida.

Contraseñas. Se almacenan con hashlib.scrypt y salt propio. El login compara contra un HASH_FICTICIO cuando el correo no existe, para que el tiempo de respuesta no revele si la cuenta existe (evita enumeración). Además, el frontend bloquea 15 minutos tras varios intentos fallidos.

Almacenamiento en el navegador. El token vive en memoria y, solo si el usuario marca "Mantener sesión iniciada", también en localStorage. Si no lo marca, cerrar la pestaña cierra la sesión. El usuario se guarda solo en memoria; el token es la única credencial persistida. El costo conocido es que localStorage es accesible desde JavaScript; las mitigaciones son React (escapa por defecto), la ausencia de dangerouslySetInnerHTML y una CSP pendiente.

8.2 Lo que la práctica enseñó

  • La base de datos es la última línea de defensa. Validar solo en el frontend o solo en el backend deja huecos; el RESTRICT, el UNIQUE y los triggers cubren lo que el código podría olvidar.
  • La normalización no es un dogma. Tres desnormalizaciones deliberadas —precio histórico, totales y tipo de cambio— resuelven problemas reales de auditoría que la 3FN pura no resuelve.
  • La seguridad por rol no basta. El caso de las figuras públicas obligó a combinar rol, confidencialidad del cliente y enmascaramiento de campos.
  • Documentar el requisito junto a la columna convierte el esquema en la fuente de verdad y facilita la trazabilidad meses después.
